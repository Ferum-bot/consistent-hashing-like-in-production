# router

Роутер перед нодами кошельков. Для клиента выглядит как один сервис wallet: те же ручки, тот же ответ. Внутри по `user_id` выбирает ноду по текущей стратегии шардирования и пересылает запрос туда.

Нода, на которую ушёл запрос, приходит в заголовке ответа `X-Routed-To`.

## Сущности

- **Топология** — список нод и стратегия, по которой между ними раскладываются пользователи. У каждой топологии есть версия. Номер присваивает chctl, у всех роутеров он общий, роутер принимает только топологию новее текущей.
- **Стратегия** — как по `user_id` выбрать ноду. Сами алгоритмы лежат в `services/libs/sharding`. Сейчас есть две:
  - `mod` — `hash(user_id) % N`;
  - `ring` — кольцо: у каждой ноды `vnodes × weight` точек на окружности, пользователь достаётся ноде первой точки по часовой стрелке от его хеша.
- **Маршрут** — что роутер посчитал для пользователя: ключ, хеш, нода, версия топологии.

## Ручки

| Ручка | Что делает |
| --- | --- |
| `GET /wallet/{userID}` | пересылает на ноду-владельца |
| `POST /wallet/{userID}/deposit` | пересылает на ноду-владельца |
| `POST /wallet/{userID}/withdraw` | пересылает на ноду-владельца |
| `GET /locate/{userID}` | на какую ноду уйдёт пользователь и почему, для кольца — ещё и точка, на которую он попал |
| `GET /topology` | текущая топология; у отстающего роутера ещё и `deferred_error`, если отложенное изменение не применилось |
| `POST /topology` | применить новую топологию |
| `POST /topology/prepare` | подготовить новую топологию: записи в переезжающих пользователей ждут |
| `POST /topology/commit` | переключиться на подготовленную топологию |
| `POST /topology/abort` | отменить подготовленную топологию |
| `POST /migrate` | скопировать переезжающих пользователей на новые ноды |
| `POST /migrate/cleanup` | удалить перенесённых пользователей со старых нод |
| `POST /bootstrap` | разложить снапшот пользователей по нодам |
| `GET /healthz` | жив ли процесс |
| `GET /metrics` | метрики Prometheus |

Swagger — на `/swagger/`, корень `/` ведёт туда же.

## Перенос данных

`POST /topology` просто переключает роутер: данные остаются на старых нодах. Чтобы при смене топологии пользователи переехали, её меняют по фазам на всех роутерах:

1. `prepare` на каждом роутере. Роутер продолжает работать по текущей топологии, но записи в пользователей, у которых сменится нода, ждут. Чтения идут к старому владельцу.
2. `migrate` на одном роутере. Он выгружает пользователей со старых нод и загружает переезжающих их новым владельцам.
3. `commit` на каждом роутере. Роутер переключается, ждавшие записи уходят к новым владельцам.
4. `cleanup` на том же роутере. Перенесённые пользователи удаляются со старых нод.

Если запись ждёт дольше `gate_timeout` из конфига (10 секунд), она получает 503 и до ноды не доходит.

Фазами управляет chctl: так применяется любой `topology.json` с `"migrate": true`.

## Отстающий роутер и защита по версии

`"membership_delay": {"router-2": "30s"}` в топологии — роутер с этим именем 30 секунд не применяет изменения, а потом применяет все накопившиеся разом. На это время он отвечает на команды 202 и продолжает работать по старой топологии.

`"fencing": true` включает защиту по версии:

- при каждой смене топологии, где защита включена, роутер сообщает её версию всем нодам (`POST /fence` у wallet), и ноды переходят в строгий режим;
- на каждый запрос к ноде роутер ставит `X-Topology-Version` — самую свежую версию, которую знает. После `abort` версия не откатывается: ноды её уже видели;
- нода отклоняет с 409 запросы со старой версией и, в строгом режиме, запросы без версии.

Топология без `fencing` после топологии с ним снимает строгий режим с нод.

Отстающий роутер при защите не может ничего записать и получает 409, пока не догонит остальных. Без защиты он пишет по старой топологии и портит данные.

Готового сценария для этого нет. Попробовать можно на переносе с четырёх нод на пять: поднять кластер `task fresh -- 05-ring-256`, затем применить копию `scenarios/06-ring-5/topology.json` с двумя дополнительными полями через `task chctl -- apply <файл>` из папки `tools`.

```json
{
  "strategy": "ring",
  "vnodes": 256,
  "migrate": true,
  "fencing": true,
  "membership_delay": {"router-2": "30s"},
  "nodes": [
    {"id": "wallet-1", "addr": "http://wallet-1:8080", "weight": 1},
    {"id": "wallet-2", "addr": "http://wallet-2:8080", "weight": 1},
    {"id": "wallet-3", "addr": "http://wallet-3:8080", "weight": 1},
    {"id": "wallet-4", "addr": "http://wallet-4:8080", "weight": 1},
    {"id": "wallet-5", "addr": "http://wallet-5:8080", "weight": 1}
  ]
}
```

Если router-2 не смог применить отложенное изменение, причина видна в `GET /topology` в поле `deferred_error` и в `task status`.

## Запуск

Из корня репозитория:

```bash
task data
task fresh -- 01-mod-3
```

`task data` генерирует 2M пользователей в `data/snapshot.ndjson`. `task fresh` поднимает кластер, применяет топологию сценария на оба роутера, очищает ноды и раскладывает по ним снапшот (`task bootstrap`). Ноды хранят данные в памяти, поэтому очистка — это перезапуск.

`task scenario -- <сценарий>` меняет только топологию: данные остаются где были.

Параметры в `config.yaml`, их можно перекрыть переменными окружения `ADDR`, `ROUTER_NAME`, `USERS`, `SNAPSHOT_PATH`, `GATE_TIMEOUT` и `UPSTREAM_TIMEOUT`. `upstream_timeout` — сколько роутер ждёт ответа ноды, после этого клиент получает 502.

Роутеры слушают `8081` и `8082`.

## Попробовать

```bash
curl localhost:8081/locate/42
curl -i localhost:8081/wallet/42
curl -X POST localhost:8081/wallet/42/withdraw -d '{"currency":"USD","amount":50}'
```
